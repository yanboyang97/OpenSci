OpenSci User and Maintainer Handbook

Use this handbook to install OpenSci, create a Study and choose the tools you want to connect. A Study is the saved record of one research question: its goal, evidence, decisions and next steps. You can begin without writing code or configuring a server.

This handbook covers OpenSci 1.1.0, revised 2026-10-15. For an introduction to the project's benefits and integrations, read the project README. Windows users can optionally remember a tunnel key and connect in the background. Before every upgrade, follow the backup checklist and update procedure.

Open OpenSci-Manual.html in the project root to read and search the English documentation offline. The files below are the maintained sources; the HTML is generated from them and should not be edited separately.

Your first successful session

  1. Follow Getting Started to install the basic software and create three small settings files. It explains where to click, what to enter and what you should see.
  2. Create one Study, read its Overview and save one progress note. At this point you have a working research record; no model subscription, Git repository or server is required.
  3. Add an AI assistant to work in natural language, or Zotero to work with your papers. Configure one integration at a time.
  4. To continue while away, follow Research from Your Phone.
  5. Use the later maintenance and technical references when you need backups, source-based research, experiments or extensions. You do not need to read them all before starting.

The OpenSci menu accepts numbered choices and short text. A ChatGPT or Codex conversation provides the AI assistant; the menu itself does not contain a language model. Each guide states its prerequisites, the actions to take and the expected result. Keep any error message and consult Troubleshooting before changing unrelated settings.

Documentation maintenance

Implementation and contracts define behavior, while configuration defines the current bindings. Documentation does not grant execution authority. When adding parameters or changing errors, defaults or record formats, update both languages, examples, tests and release hashes together. A documentation revision is distinct from a code version, Git commit and record schema_version.

See the documentation workflow for rebuilding and checking. Replace example placeholders with real values. Sections marked for later enablement describe prerequisites and procedures, not completed setup. Update deployment status only after accepting a newly enabled capability in the actual environment.

Separate language editions

The Chinese handbook and Chinese offline edition are maintained separately. The English offline edition collects all English guides and references. No machine-specific account, SSH alias or private user path belongs in either edition. Configuration examples are placeholders; preserve actual bindings only in ignored local files.

A Coordinator is the sole writer of formal study records. A Development Workspace holds the reviewed source used for evidence work and development. An Execution Node hosts a human-approved experiment. These are deployment roles, not editions of OpenSci. Choosing a workspace never moves an experiment or changes its node.

Availability and operating limits

  • Installing OpenSci does not create Git identity/history, grant library access, enable models or start resident services. Complete the setup for the feature being used.
  • Run Monitor and Assistant Access require deliberate deployment and account isolation. Chat agreement and process identity do not establish independent human approval.
  • Library APIs, browser collection, native citation editing and scanned-material coverage depend on the installed applications and access rights. Inspect each operation's coverage and status; unavailable integrations remain explicit.
  • Back up Zotero separately; OpenSci archives do not include the external library database and original attachment storage.
  • Simulations validate software behavior. Production scientific tools, GPU execution and autonomous research services are outside the supplied runner's scope.

Study connections

Study Overview (menu 10), Save Discussion Progress (menu 11), protected native project links and the single-Study private Chat path are described in Study connections. The OpenSci Study plugin and Study MCP Server connect to an explicitly selected private Study. Native project identity is used only when a trusted host supplies it; otherwise it remains unknown. No automatic Work dispatch, extra model calls or experiment submission is part of saving.

Plugins and MCP

Handbook · Requirements

Connect an assistant so it can read your Study Overview and save progress when you ask. This tutorial covers ChatGPT, Codex, Claude Desktop and Claude Code. MCP is the connection protocol; OpenSci's local server is scripts/hub_mcp.py. The OpenSci Study plugin packages that server for compatible plugin hosts. Neither installation method creates your Study or supplies an account, tunnel or credentials.

Keep Zotero on the coordinator's computer; never forward its local port. For phone task continuation see Research from Your Phone.

1. Prepare one selected Study

First complete Getting Started, create a Study and confirm that you can read its Overview locally. You need Python 3.10+ and the full OpenSci software folder. Direct MCP needs no MCP SDK or extra Python package. Have these four values ready:

Value Beginner Windows example Where to find your value
Python executable C:/Tools/Python/python.exe python in software config/runtime.local.json; macOS/Linux: command -v python3, then check its version
Software folder C:/OpenSci Folder containing scripts/hub_mcp.py
Records folder C:/OpenSci-Data Your selected folder containing config/hub.local.json and saved Studies
Study ID STUDY-001 ID shown after creating/listing your Study

On macOS use your own paths, for example /Users/yourname/OpenSci and /Users/yourname/OpenSci-Data; on Linux, /home/yourname/OpenSci and /home/yourname/OpenSci-Data. Replace yourname and every sample path with a real absolute path. In JSON/TOML arguments do not use ~ or shell variables: they are not automatically expanded.

Copy software config/mcp.unselected.example.json to records config/mcp.policy.local.json. Open the copy in a text editor and replace connection_id with a unique label, such as opensci-codex-01. Keep the other fields unchanged for now. This label is not a password. When connecting a second client, make a separate policy file and connection ID, for example mcp.claude.local.json / opensci-claude-01, and use that path in its commands. All clients can point to the same authoritative records folder; do not copy the Study to each client.

Stop the connection before selecting its Study. On first setup it is not running yet. In PowerShell:

Set-Location -LiteralPath 'C:\OpenSci'
$OpenSciPython = (Get-Content -LiteralPath '.\config\runtime.local.json' -Raw -Encoding UTF8 | ConvertFrom-Json).python
& $OpenSciPython -E -s -B scripts/select_study_connection.py --coordinator-root C:/OpenSci-Data --policy C:/OpenSci-Data/config/mcp.policy.local.json --study-id STUDY-001 --connection-stopped

On macOS/Linux, run from your software folder, substituting actual paths:

/usr/bin/python3 -E -s -B scripts/select_study_connection.py --coordinator-root /home/yourname/OpenSci-Data --policy /home/yourname/OpenSci-Data/config/mcp.policy.local.json --study-id STUDY-001 --connection-stopped

Study selected. confirms selection. This also enables permitted agent writes. For a read-only connection, set allow_write back to false in the policy before launch. Leave allow_remote_checks false for the first read. The identity/context fields remain unknown unless you have a trusted host binding; a model's name is not proof of project identity.

2A. Codex: connect the local server

Use either the direct connection here or the plugin route below for a given client, so you do not accidentally expose duplicate tools with different identities.

Codex keeps MCP entries in ~/.codex/config.toml by default (%USERPROFILE%\.codex\config.toml on Windows). If you configured a different Codex home, use its active file. Back up the file and merge only the following table, preserving other settings. If the name already exists, review that entry rather than adding a duplicate. Official MCP configuration

[mcp_servers.opensci]
command = 'C:/Tools/Python/python.exe'
args = ['-E', '-s', '-B', 'C:/OpenSci/scripts/hub_mcp.py', '--coordinator-root', 'C:/OpenSci-Data', '--policy', 'C:/OpenSci-Data/config/mcp.policy.local.json']
cwd = 'C:/OpenSci'
startup_timeout_sec = 20
tool_timeout_sec = 60
enabled = true

Replace the executable and paths with step 1's values. On macOS/Linux change all paths, including cwd, to native absolute paths. The reusable template is mcp.desktop.example.toml.

Restart the local client/server and start a new conversation. In Codex CLI run codex mcp list, then /mcp inside Codex to inspect the active connection. A desktop host exposing Settings → MCP servers can add the same STDIO command/arguments and restart it there. Complete the common acceptance steps below; a listed configuration alone does not prove a successful read. Local configuration does not automatically connect a hosted/cloud chat.

Optional: install the OpenSci Study plugin

Use this only in a client supporting OpenAI's plugin format. The repository root contains plugin.json, mcp.json, assets and the server; .agents/plugins/marketplace.json points to that root. Python must be launchable as python in the host environment. If you need an absolute Python path, use direct MCP instead.

Copy config/plugin.connection.example.json into a new OpenSci/connection.json under %LOCALAPPDATA% on Windows. Press Windows+R and enter %LOCALAPPDATA% to open that location. On macOS/Linux the OpenSci entry script uses ~/.config/opensci/connection.json; alternatively set OPENSCI_CONNECTION_FILE to an absolute file path in the host process. Edit only your actual values:

{"schema_version":1,"coordinator_root":"C:/OpenSci-Data","policy":"C:/OpenSci-Data/config/mcp.policy.local.json"}

Save UTF-8 without an extra .txt suffix. Keep this operator-owned file outside plugin caches; missing or invalid settings stop the plugin. In a compatible Codex CLI use codex plugin marketplace add yanboyang97/OpenSci, then codex plugin add opensci-study@opensci if supported by that installed version. A compatible desktop marketplace can select and install OpenSci Study from the repository. If the command/UI is unavailable, use direct MCP above and consult the current plugin guide. Start a new conversation after installation. The GitHub download does not imply a public directory listing or provision a hosted service.

2D. ChatGPT: connect your private tunnel

ChatGPT in a browser cannot launch your local Python command directly. Run the official Secure MCP Tunnel client on the computer holding OpenSci, using a separate selected policy. You need access to the intended Platform organization and ChatGPT workspace. Creating a tunnel requires Tunnels Read + Manage; the runtime key and connector operator need Read + Use. Associate the tunnel with the target ChatGPT workspace as well as its owning organization. Official tunnel setup

Prepare the tunnel profile

Open Platform tunnel settings, create/select your private tunnel, and record its tunnel_id and organization ID. Download the official client for your OS from that page or its linked release. Keep the binary in a chosen folder. Confirm its published provenance/checksum where supplied and inspect help quickstart; OpenSci does not redistribute this client.

For a Windows example client at C:\Tools\tunnel-client\tunnel-client.exe, run:

& 'C:\Tools\tunnel-client\tunnel-client.exe' help quickstart
& 'C:\Tools\tunnel-client\tunnel-client.exe' init --sample sample_mcp_stdio_local --profile opensci-chat --tunnel-id YOUR_TUNNEL_ID --mcp-command 'C:/Tools/Python/python.exe -E -s -B C:/OpenSci/scripts/hub_mcp.py --coordinator-root C:/OpenSci-Data --policy C:/OpenSci-Data/config/mcp.policy.local.json'

Replace the tunnel ID and all paths; if a path contains spaces, preserve the quoting required by the client's help. Note the generated profile's actual absolute file path from its output. The profile is the local file telling the tunnel how to start OpenSci; do not assume it is named chat.local.yaml.

For macOS/Linux, use the official native binary's absolute path with the same init options and your native Python/server/records/policy paths. The --mcp-command value remains one quoted command string. If initialization requests credentials, supply them locally using the protected process-environment method below; never put a literal key in command history or the profile.

if (Test-Path Env:CONTROL_PLANE_API_KEY) { throw 'Use a fresh terminal without an existing tunnel key.' }

Optional: remember the key and connect in the background (Windows)

OpenSci 1.1.0 adds an optional saved-key mode. The existing one-time prompt remains available. This key connects the tunnel; it is separate from keys used to call a model. Windows DPAPI (the Windows facility for encrypting data for your signed-in account) encrypts the key on this computer. OpenSci never generates a real OpenAI key locally or extends its expiry.

  1. Complete the tunnel profile and config/chat.local.json setup above. Stop the old tunnel window with Ctrl+C. Keep only one client for this tunnel.
  2. Open the official Platform tunnel settings and follow OpenAI's runtime-key guidance. Select the same organization as your tunnel. Create a dedicated restricted API key with Tunnels Read + Use only. Select a long expiry that the account permits, or no expiry only if that option is actually available. Keep the organization and ChatGPT workspace association unchanged. If the permission or expiry option is unavailable, ask the organization administrator; do not substitute a broad model/admin key.
  3. In File Explorer open your OpenSci installation folder and double-click Manage-Study-Connection.cmd. Enter 1. A small Windows form opens. Paste the new key into its masked field once. Do not paste it into a conversation, a command, or a JSON file. Record the platform expiry in the optional YYYY-MM-DD field; a blank field does not remove platform expiry.
  4. Leave Start automatically after I sign in to Windows checked if desired. Click Save encrypted and connect. The key is saved under %LOCALAPPDATA%\OpenSci\connections\<connection-id>\credential.dpapi; the form never saves a plaintext key. The private folder is restricted to your Windows account and SYSTEM. The optional sign-in entry is named OpenSciStudy-<connection-id> in your user's Windows Run settings; it contains paths, never the key.
  5. In the connection menu enter 2 Status. Wait briefly and check stored_key: true, worker_running: true, client_running: true, and ready: true. With auto-start selected, start_at_sign_in is also true. Finally ask the ChatGPT connection to read your selected Study Overview. A healthy client alone does not prove the ChatGPT tool call works.
  6. Close the setup/menu window. The background process continues. On subsequent Windows sign-in it starts automatically if selected; otherwise double-click Start-Study-Chat.cmd to start it without re-entering the key. This is a per-user background process, not a system service: the computer must remain awake and online, and the user must remain signed in. Locking the screen is different from signing out. A sleeping/offline computer cannot serve live requests.

The background worker supplies the decrypted key only to the tunnel child's process environment. It checks the client checksum and binds the stored credential to the configuration path, organization, client hash and profile hash. Ordinary OpenSci updates at the same installation path retain these settings. Changing the client or profile requires reviewing the new values and saving the key again. The client handles transient network reconnection; if the client exits, the worker tries at most five launches, with increasing delays, then reports attention_required.

Getting Started

Handbook · All software requirements

Your first goal is simple: create a Study, save a progress note and read it back. A Study is a saved research question with its evidence, decisions and next steps. This first session needs Python and the OpenSci files. AI accounts, Git, Zotero and servers can be added later.

The steps below use Windows. Linux users can use the short section near the end of this guide. If someone has already set up OpenSci for you, go straight to Create your first Study after confirming which folder holds your records.

Running the later examples

Direct Python examples use the session function below. Paste the complete block once into a PowerShell window and use Invoke-OpenSci in that same window. It selects the project's Python and Git, then restores PATH and the working directory after each call. It does not need to be added to your personal Profile.

function Invoke-OpenSci {
    param([Parameter(Mandatory=$true)][string[]]$Arguments)
    $OpenSciRoot = 'C:\OpenSci'
    $OpenSciRuntime = Get-Content -LiteralPath "$OpenSciRoot\config\runtime.local.json" -Raw -Encoding UTF8 | ConvertFrom-Json
    $OpenSciPreviousPath = $env:PATH
    $OpenSciPreviousLocation = Get-Location
    try {
        if ($OpenSciRuntime.git) { $env:PATH = (Split-Path -Parent $OpenSciRuntime.git) + [IO.Path]::PathSeparator + $OpenSciPreviousPath }
        Set-Location -LiteralPath $OpenSciRoot
        & $OpenSciRuntime.python -B -X utf8 @Arguments
        if ($LASTEXITCODE -ne 0) { throw "OpenSci exited with code $LASTEXITCODE" }
    } finally {
        $env:PATH = $OpenSciPreviousPath
        Set-Location -LiteralPath $OpenSciPreviousLocation.Path
    }
}
Invoke-OpenSci -Arguments @('scripts/hub.py', '--coordinator-root', 'C:/OpenSci-Data', 'list')

The helper does not itself authorize SSH, model calls or study writes; the selected command determines the effect. Bare python -B scripts/... examples in reference chapters assume a configured interpreter, Git on the session PATH and the project root as the working directory. On Windows, pass those script arguments to Invoke-OpenSci as shown above. On Linux, use /usr/bin/python3 -B from /home/researcher/OpenSci and adapt paths. The remote copy is not designated to perform coordinator writes.

Git prerequisites for source-dependent work

When the research workspace needs Git provenance, confirm the commit name, email and whether a shared Git repository will be used. Configure identity in the project repository rather than globally. Review the staged source, excluding machine configuration, credentials, real study state and run artifacts, then create the initial commit.

Matching commits are still required if both origins are absent.

A trusted host may supply native project identity. Without that context, the connection remains scoped to one explicitly selected Study and reports its source as unknown.

A Study can register a research workspace when creating a Study. Adding or replacing that workspace after creation is not yet exposed as a supported operation. Existing Studies created without source provenance can continue discussion and literature work; their source-dependent checkpoints and experiment preparation remain blocked. Do not edit the stored workspace or anchor manually.

The initial connection selects exactly one Study. Native project type, Chat/Work mode, execution host and conversation reference remain unknown when the host does not supply trustworthy context. Tools and bounded context

Tool Behavior
opensci_get_capabilities Protected scope, enabled operations, identity limitations and connection status; no inferred usage

opensci_get_study_brief Deterministic saved overview, revision, digest and time; at most 8192 UTF-8 bytes in its JSON value

save_progress takes exactly arguments: {"progress": {...}}. Progress has summary plus five string arrays: decisions, hypotheses, evidence_refs, open_questions, next_steps. The summary permits 16000 UTF-8 bytes; each array permits 64 items of at most 4000 bytes; the whole progress object is limited to 48000 bytes and the command to 64000 bytes. Evidence strings are references, not assertions that files were read. The service attaches only protected source context. Original conversations stay in the native app.

Each save replaces the entire current progress object; it does not append to the previous summary or retain lists sent as empty arrays. Read the latest progress, including omitted detail, and carry forward content that should remain current. Earlier versions stay in history; follow progress and history to read them.

Overviews remove whole fields when needed and return has_more and revision-pinned detail references; they never truncate JSON silently. Record heads remain limited to 4 MB. Input and output MCP frames are limited to 256000 bytes. Capacity rejection preserves the old head. Saving calls no model and does not poll transcripts.

Native project links and Work

The management channel is the local protected Operation Service CLI under an operator identity. bind_project takes binding; unbind_project takes identity. A binding contains identity, display_name, availability. Identity has exactly provider, namespace, project_id, project_type (chatgpt_project, local_folder, remote_folder) and host_id. Availability is available, unavailable or unknown.

Obtain native IDs from trusted host tools or explicit operator onboarding. One native project links to one current Study; multiple native projects can link to the same Study. Rename by updating the display value for the same identity. Temporary invisibility marks availability; it does not delete the Study. A copied folder or new worktree does not inherit a link or grant. Rebind using two separate receipted operations: unlink the old Study, then bind the new one. The intermediate unlinked state remains visible.

Links live inside authoritative records. The reverse index is rebuilt from heads on demand. Both coordinator and Study locks cover uniqueness checks and the single atomic commit. Create-and-bind uses one commit. Grants and links are separate: a missing grant or unavailable link never counts as ready. Multi-Study writes require protected native project context; model-supplied IDs do not select a broader write scope.

Local Work can use config/mcp.desktop.example.toml with the coordinator and policy paths. Remote Work needs the restricted fixed-command transport in config/mcp.remote.example.toml to the same coordinator. That example does not provision SSH accounts, keys or Windows SSH service. Do not create a second writable remote copy. Sharing a native project does not grant OpenSci access. Native project creation or instruction editing remains a host/UI step when no supported API exists; preserve existing instructions.

Remote access when the coordinator is a local computer

If the remote host cannot run a fixed command on the coordinator directly, an operator can use scripts/study_remote.py with an SSH reverse forward. The server binds only 127.0.0.1, checks a 32-byte random token encoded as 64 lowercase hex characters before opening an MCP session, fixes the coordinator and policy, caps sessions at eight, and retains the existing MCP frame and operation limits. Tokens are separate from OpenAI keys. Store them with owner-only permissions and do not place them in commands, project files, logs or examples.

  1. Provision an SSH connection with host-key verification. Check existing forwards first; do not interrupt or overwrite another session's forwarding configuration.
  2. Start study_remote.py server --port COORDINATOR_PORT --token-file PROTECTED_TOKEN --coordinator-root STATE_ROOT --policy PROTECTED_POLICY --ready-file NEW_READY_FILE on the coordinator. For a port chosen by the OS, pass --port 0 and read the local ready file. The policy should identify the dedicated private connection and verified remote entry.
  3. Establish an operator-owned SSH reverse forward from remote 127.0.0.1:REMOTE_PORT to coordinator 127.0.0.1:COORDINATOR_PORT, with ExitOnForwardFailure=yes. Do not expose either port publicly. Deliver only the stdlib study_remote.py client and the per-connection token over the authenticated channel; do not copy coordinator records or OpenAI credentials.
  4. Use config/mcp.ssh-loopback.example.toml on the remote host. A fixed-command Work entry may invoke the same client. The remote client has no authority to select another coordinator or policy. Read capabilities and resolve the Study before saving.
  5. After disconnection, re-establish the same scope and query the original receipt. Stop the gateway and SSH forward when no longer needed, remove the temporary token on both endpoints, and remove the ready marker only after verifying that its process has stopped. The helper does not install a service or auto-start rule.

The plain loopback transport relies on the authenticated SSH channel for encryption and host verification. It is not a public MCP endpoint or multi-user server. Same-account filesystem access is not a security boundary.

For handoff, read the latest Study ID, revision, goal, selected evidence, questions and next steps. Local/remote Work may perform reading, analysis, planning, writing and development directly, with no Chat prerequisite. Switching entry points does not transfer complete transcripts, file permissions, uploaded files or running processes. Report unavailable files honestly. Actual host/model usage remains unknown unless reliably reported; no fixed percentage of savings is promised.

Upgrade and recovery

New Studies are ready for structured progress. If an imported record reports that preparation is required, use the named operation in that diagnostic and the preflight/apply procedure in Maintenance Plans. Stop all writers, verify a backup and reconcile original run IDs first. Preserve original bytes and history; never change format markers manually. Keep compatible source available for recovery.

After a timeout, query the original receipt through the same trusted principal and role. A private Chat connection receipt uses its configured connection principal; a local --agent OS identity is not interchangeable. After a revision conflict, read differences and prepare a deliberate new intent. Offline drafts stay unsaved until reconciled.

This includes configured state/evidence/history and selected local policies; it excludes runtime software, external research folders, credentials and connection processes. Verify and restore into a new directory. Restoration never activates another writer. Planning rollback creates a new revision and preserves later receipts/evidence/runs; it does not erase later records or move external processes.

Literature Workspace

Handbook · Exact operations and limits

This tutorial takes you from one paper in Zotero to a checked citation in a manuscript. Zotero holds the papers, attachments and personal notes. OpenSci records which evidence a Study used, what was screened, and what was saved. A search produces candidates; it does not add them to your library.

Start with connecting and reading one paper. Continue to search and collect, read and organize, optional analysis, citations, or recovery when needed. You can stop after any completed step.

On macOS/Linux use your actual absolute paths and Python 3.10+; the Windows launchers and native Word workflow are separate integrations.

LaTeX / BibTeX and Quarto

Create a working folder under C:\OpenSci-Data\manuscript\, for example manuscript/paper-01/, and copy the needed sample and bibliography there. For the citation example below, name your working manuscript draft.tex (or draft.qmd).

(Get-FileHash -LiteralPath 'C:\OpenSci-Data\manuscript\paper-01\draft.tex' -Algorithm SHA256).Hash.ToLowerInvariant()

{"manuscript_id":"paper-01","path":"manuscript/paper-01/draft.tex","expected_sha256":"SAVED_FILE_SHA256","format":"latex","item_refs":[{"binding_id":"personal-library","item_key":"ABCD1234"}],"marker":"OPENSCI_CITE_HERE_01"}

With the appropriate toolchain already installed, open a terminal in the working manuscript folder.   1. On the local desktop with Word and Zotero's Word plugin available, create the records folder's manuscript directory if needed and save a copy as C:\OpenSci-Data\manuscript\draft.docx. Insert OPENSCI_CITE_HERE_01 once outside existing citation fields, save, and obtain its hash as above.
  2. Submit literature.cite with the same fields as the text example, but path: manuscript/draft.docx, format: word, and phase: prepare. Use actual item references. Read the resulting task and retain task_id. waiting_local means Word still needs attention.
  3. You or an authorized desktop assistant must observe the actual document path/window. Select only the marker, use Zotero Add/Edit Citation, select the real requested paper, and save.   4. Compute the new saved hash. Submit a new literature.cite request keeping the original manuscript, path, item references and marker, adding task_id, changing phase to verify and setting expected_sha256 to the new hash. A succeeded result verifies saved field structure and edit scope.

Extending an offline simulation adapter

Register an instance under an ASCII name in REGISTRY in scripts/simulation_adapters/__init__.py. The instance provides api_version=1, version, prepare(parameters), execute(prepared) and validate(prepared, result). A name attribute is not required; the registry key supplies the name.

Use the Sum Calculation (sum-v1) and Quadratic Calculation (quadratic-v1) implementations as executable references. Reject unknown fields, non-finite or oversized inputs and booleans masquerading as numbers; produce bounded serializable output and validate it independently. Never load caller-selected modules or accept arbitrary shell commands.

Method Contract
prepare(parameters) Validate and normalize inputs for the frozen request
execute(prepared) Produce results; no scheduling or approval authority
validate(prepared, result) Return whether the result meets the adapter's validation rules

Requests freeze the adapter class's file and the engine file, not every imported dependency. Define a reproduction strategy when introducing dependencies. Changed code may prevent even querying an old request; preserve matching old source for inspection and prepare new requests/IDs for new code. advance is explicit and has no background daemon.

Cover valid input, rejection boundaries, identical retries, conflicting ID reuse, cancellation, process recreation, artifact tampering and refusal to rerun interrupted work. See the simulation guide for the complete workflow.

Extending unified commands

A new command must define exact argument fields, permitted roles, write/remote-check prerequisites, revision rules, transaction behavior and receipt semantics. Keep global CLI options before subcommands. Adding MCP access requires a separate tool schema and dispatcher change; do not automatically expose all CLI capabilities.

Test denied roles, unknown fields, stale revisions, identical retries, ID reuse with changed content/identity, lock conflicts, unknown outcomes and damaged history. Recover committed:null by querying the original receipt rather than replaying under a new ID. Experiment approval/submission must not be casually added as ordinary agent commands.

Extending model configuration or protocols

Existing automated-review kinds are codex, claude, gemini and openai_compatible. Adding a configuration for an existing kind differs from implementing a protocol. The former still requires account/model/endpoint/budget/completion acceptance; the latter also changes configuration validation, environment allowlists, invocation, completion detection, output records and tests.

The compatible endpoint appends /chat/completions to base_url and does not add /v1 automatically. Truncation, refusal, tool requests or missing completion evidence must not become a successful review. Maintain the Windows interactive Claude .psd1/DPAPI chain separately; see the launcher guide.

Production-software integration scope

Production tasks currently accept only the public estimator example, fixed data definitions, one CPU and zero GPUs. Scientific-software or GPU integration requires coordinated task/approval contracts, resources/licensing, execution, timeout/cancellation, artifact acceptance, environment binding, observation/recovery and actual scientific validation. This defines the extension boundary; it does not provide or enable that capability.

Literature Workspace Reference

OpenSci 1.1.0. Literature Workspace connects literature search, a personal Zotero library, evidence snapshots, bounded analysis and citation writing. The daily guide explains the workflow; this reference lists exact operations and integration limits.

Ownership and deployment

Zotero owns the personal library, collection tree, original attachments, single-paper notes and native annotations. OpenSci owns study associations, search attempts, immutable evidence snapshots, derived indexes, jobs, usage, cross-paper results and manuscript mappings. No OpenSci setting controls Zotero's storage directory or sync policy. Group-library operations are rejected.

The existing coordinator remains the only study writer. Its local Windows context handles Zotero, campus/browser access, PDF extraction and Word. The configured SSH development node receives bounded immutable evidence for explicitly dispatched analysis. It never receives a forwarded Zotero port, Windows grant, browser session or a continuous PDF mirror. A remote worker cannot write the study head. Results become formal only after coordinator verification and import.

Searches, import and library writes

PubMed uses ESearch/EFetch and retains original article XML. Web of Science uses its Starter API; Scopus and IEEE use their official metadata APIs when separately authorized. API credentials are not inferred from campus web access. Google Scholar uses a browser-assisted path and native per-record export; no generic bulk API is claimed. Unsupported adapters remain not_executed.

Each source attempt preserves its literal query, adapter version, timestamp, sort, cursor, requested window, candidates, capabilities and coverage. Failures are isolated; zero_results is distinct from permission_denied, waiting_user, partial and unavailable. Resume preserves the original query/settings and appends history. A native export is deliberately partial: it cannot prove the entire external search was exhausted. RIS must be terminated; BibTeX accepts explicit values and nested braces, and rejects macros/preambles/concatenation rather than silently changing their meaning.

Only explicit collection requests create Zotero items. Strong DOI/PMID matches also require title/type consistency; ambiguous identifiers or title-only matches wait for review. Existing records are reused with additive collection/tag changes. Original user notes remain untouched; new AI notes are separate objects labeled with the generating request. Reanalysis creates another note version. New PDF annotations require explicit operator permission and position data; reading never creates highlights.

Creates use deterministic object keys, version zero, an external intent journal and a post-write read. Updates/deletes bind the current local object version. The external journal distinguishes intent, started, verified, rejected and unknown outcomes. A crash after a possible write never causes an unconditional resend. Batch results retain each successful item and each failure. reconcile creates a new coordinator receipt while reusing original external intent IDs; original result blobs remain immutable. An unresolved intent remains outcome_unknown. A known rejected change needs a reread and a newly reviewed intent.

Field/note replacement, relationship removal and deletion require a concrete preview and confirmation digest. A newer manual edit invalidates the preview. Native merging is intentionally handed to Zotero, followed by survivor/reference reconciliation; copying fields then deleting another item is not a supported merge.

Full text and evidence

PDF acquisition validates HTTPS destination, media type, magic/end markers, bounded size and checksums. Generic downloads reject private-network destinations and redirects. The fixed official PMC bucket supports licensed article versions, checks DOI/PMID, selects a published version from its listing and verifies its recorded PDF MD5. It does not infer subscription entitlement. Publisher login/CAPTCHA or unavailable full text waits for browser/user assistance. Attachment creation/upload uses Zotero's API; no direct storage-file writes occur. Metadata may succeed while full text remains missing.

Discovery snapshots contain metadata/abstracts. Regular/deep snapshots add available notes, native annotations and extracted PDF text, retaining attachment bytes' SHA-256, parser/version, one-based PDF pages, separate printed labels and failed pages. PyMuPDF is optional. No OCR, image understanding or formula verification is inferred from text extraction. Scans and failed pages are reported for OCR or visual reading; deep_verified remains false until separate scientific checks. Annotation read failure does not suppress otherwise available attachment parsing.

Snapshots use content-derived IDs excluding their own ID field. Exact manifest/file bytes are validated on publication, transfer, load and model/result processing. They are historical evidence even after a Zotero edit or deletion. The local SQLite FTS5 index is derived and rebuildable. A full versions-map digest conservatively invalidates cached freshness after new children or library edits; deleted/changed/unrevalidated rows are not presented as current. Parsing and indexing are explicit operations, not a background whole-library synchronization service.

Model prompts receive only evidence in the selected snapshot: metadata, abstracts, readable text pages, separately attributed notes/annotations and coverage. Failed pages are excluded. Claims require item identity, attribution, attachment hash and an actual page or note/annotation version. Missing abstracts, unparsed attachments, failed pages, invented printed labels and self-certified model verification are rejected. Structural validation cannot establish scientific truth; humans still check conditions, counterexamples, equations, figures and conclusions against originals.

Jobs, costs and recovery

Analysis first creates a persistent queued job and reservation; dispatch is a separate explicit step to the existing SSH node. A complete checksum-verified snapshot is required before the detached worker launches. Job/attempt/generation/node/snapshot bindings prevent stale results and duplicate execution. A launch marker with unknown outcome stops takeover; confirmed dead-process recovery reuses the original attempt. Closing chat does not stop a dispatched worker. Local offline actions wait; the remote uses only its received snapshot. No recurring search, new service, compute/GPU authority or alternate node is enabled automatically.

Paid work requires finite request, token, estimated-cost and concurrency ceilings plus a named global accounting period. Unsettled reservations remain charged across disconnection and are not reallocated. Smaller limits prevail. The executor reuses an enabled openai_compatible, gemini or claude provider with tools disabled. Supply its ordinary config/providers.local.json locally on the executor, and a versioned literature_price_per_million object with input, output, revision. No provider secret is transmitted from the coordinator. Input uses a conservative UTF-8-byte allowance; provider output tokens are bounded. Oversized context waits for a smaller batch/budget. Architecture and boundaries

OpenSci combines one command service, durable file records, an independent observer, bounded reviews and human-approved execution. CLI and MCP share business rules; the desktop is an access layer, not a core runtime dependency. Development and execution are linked through fixed source commits, evidence digests and run IDs. History and Recovery

Study history and capacity

History and Recovery preserves study revisions and provides deliberate maintenance plans for source updates, workspace transfers and planning recovery. These operations do not move processes, start experiments or extend approvals.

The current record is coordination/projects/<study_id>.json. Before each update, the full prior bytes are retained in history/<study_id>/<sha256>.json; the head links backward by digest. Checkpoints, phases, sources, runs and device bindings can be traced. Atomic head replacement is the commit point; an unreferenced snapshot is not committed history. Snapshot publication uses non-overwriting Windows rename or POSIX hard links after writing/syncing/checking. Validate real filesystems. Crashes may leave .snapshot-*.tmp or uncommitted snapshots; stop writers and reconcile the chain before handling them. History is not automatically deleted. Local locks/checks do not guarantee against malicious changes, distributed writers or every hardware failure.

Current reads/writes share a 4,000,000-byte UTF-8 limit; show warns near_capacity at 80%. Oversized serialization is rejected while preserving the old head. History is separate, but run/reference indexes still occupy the head; capacity is not unlimited. Store long materials externally and plan archival for large studies. Backups retain a separate 4 GiB limit. History pages run newest-first; use next_before_revision and stop at an empty page. Updates, migration plans and backups verify the reachable chain, so costs grow with history.

Inspect records safely

record_reader.py requires a trusted original SHA-256 and reports both content and validation scope. It never renews approvals, writes records or submits tasks. Keep frozen review inputs and artifacts together. A readable expired approval remains expired; unknown formats are rejected.

For a restored record that requires preparation, preserve its original bytes and use maintenance preparation. Missing history must remain explicitly unknown. A maintainer can use --legacy-large for read-only inspection or maintenance preflight of an oversized record, up to 64,000,000 bytes. Application still requires a resulting record within the normal limit; never truncate records to force acceptance.

Changes to source, shared rules or the execution environment require appropriate new tasks and human approval. Reconcile existing runs by their original IDs on their original nodes.

Upgrade and relocation

Stop all writers/autosaves, preserve source and a verified backup with an independent digest, and handle external assets separately. Restore into a new directory and keep the original read-only. Reapply the same reviewed origin because backup does not restore Git configuration. Review new source in the restored history, preserve study/local state and commit. Do not replace the study's identity with an unrelated repository.

Fill actual destination account, absolute workspace and Python in local configuration. Generate an external lifecycle preflight plan, review study/source revision/digest, target commit/config/device and original runs, then apply the exact plan digest. For remote targets, explicitly add --allow-remote-check to both preflight and apply after connection authorization. Plans last one hour. Application rechecks inputs under global/study locks; changes require a new plan. Quiesced/backup-saved/runs-reconciled are human assertions, not actions or distributed locks performed by the tool.

Successful upgrade keeps study_id, advances revision and preserves historical evidence/approvals/runs while recording the selected source and Development Workspace. No process is moved, restarted or resubmitted. Read history/show before authorized resume. Use operation relocate for changed account/path with unchanged code; it requires a writable study record and the recorded commit/origin. When the previous Development Workspace is unavailable, humans must first confirm writers stopped and reconcile every original run. Upgrading code at the same time uses upgrade with a destination. Old device bindings stay in history; the selected Execution Node and previous task nodes stay unchanged. Reaccept credentials/licenses/ACLs on new devices. Corrupt identity/history or unknown run ownership blocks automatic continuation and requires human recovery.

Planning history and source versions

Plan rollback restores goal/phase/checkpoint_note from an earlier committed revision into a new higher revision. It retains later runs, references, approvals, source and device bindings. Old experiment_running becomes analysis rather than implying a live job. Use lifecycle preflight operation rollback with to-revision, reviewed reason and a new plan.

Historical source versions are managed through retained release packages or Git history. OpenSci has no dedicated command to recover an older source/state release. Ordinary backup and restore remain available for a separate recovery directory; verify source compatibility, current records and original run IDs before any writer handover.

Shared rules and limits

Maintain only root AGENTS.md for both development clients. Historical deliveries remain unchanged. Automated review injects and freezes the same rules in rules.snapshot.md, which is immutable evidence rather than a second maintained source. Check actual interactive rule loading and ancestor-rule precedence for the installed client. This deployment does not alter user-level client settings. Automated review relies on explicit injection.

The framework supports one writer, a small number of execution nodes and a scale humans can reconcile. Storage/lifecycle are separated and source/state/device settings can be recovered separately. The literature SQLite index is derived and rebuildable. Distributed leases, authenticated experiment approval, recurring scheduling, license management and scientific acceptance are not established by offline test success.

Literature history

Literature Workspace stores registered references to separate immutable evidence and operation records. Retain external effects, receipts and evidence during recovery. Restoring OpenSci source does not undo Zotero writes or native Word edits. Preserve the whole coordination/literature/ directory and manuscripts, then reconcile the actual library instance before further writes.

Serialization and task contract

Runtime data comes from scripts, never inferred chat memory. JSON is UTF-8, rejects duplicate keys and NaN/Infinity, and uses temporary-file replacement. Task/approval hashes bind original bytes. Nested review/environment/limits and plans use common.canonical: sorted keys, two-space indentation, Unicode retained and a final newline; this is the project convention, not RFC 8785. Do not reformat approved records. The executable authority is scripts/task_contract.py.

Approval

Bindings are run_id, task_sha256, git_commit, environment_sha256, node, limits_sha256, evidence_sha256, protocol_sha256 and review_sha256. Environment_sha256 covers the complete canonical task.environment, including interpreter identity. A real human fills decision=APPROVED, approved_by, approved_at_utc, expires_utc and rationale. Approval cannot predate task creation or be future-dated. Expiry is rechecked at preflight, after locking and immediately before process launch; it must cover startup, not the entire subsequent execution. Expiry during a running job does not cancel it.

The run command's --approve is the approval file's raw 64-character lowercase SHA-256, not the task hash. Invalid/empty values are rejected before a run directory is created. JSON is an audit record, not a digital signature or identity system. An account with write access can forge it; protect originals and submission rights through separate human-owned accounts. Test approvals are offline fixtures only.

Environment

Capture on the actual target with the selected interpreter. Preparation checks schema, hostname, Linux and absolute invocation path. Execution recollects and compares spec and interpreter. Preserve a virtual environment's invocation path; realpath is recorded separately and must not replace it. Python/package versions, paths, prefixes, OS and architecture must match. Prefect uses the worker's explicit OPENSCI_EXPERIMENT_PYTHON, not its own scheduler environment.

The fingerprint is not a reproducible image: wheel bytes, system libraries, GPU drivers and hardware equivalence are not fully verified. Platform text is diagnostic; kernel version is not a forced-equality field. Real adapters need data digests, dependency locks/image hashes and hardware acceptance. Capture excludes environment-variable values and credentials; protect environment/lock records according to project sensitivity.

Status and recovery

Status transitions starting → running → completed, failed, launch_failed, timeout, cancelled, failed_validation_or_runtime, initialization_failed or cleanup_failed. Persistent record failure returns recording_failed with status_persisted=false and status_sha256=null; this result may never reach disk. Terminal states retain finish time, exit code and available artifact hashes; completed requires all six artifacts. Heartbeats update about every two seconds, increasing source_sequence from 1. Statuses without a source sequence use conservative time/digest observation. SIGINT/SIGTERM/timeout clean up the entire child process group before final recording.

Power loss, SIGKILL and disk failure can prevent final writes. inspect_run diagnoses stale/absent/corrupt/initialization-failed state and lists leftovers, without proving death or restarting jobs. Humans reconcile actual host, PID ownership, scheduler, logs and output. A further attempt needs a new run ID and approval. There is no central authenticated approval database, distributed lock or automatic process recovery.

Study Record

Current study JSON records goal, phase, revision, optional research source commit/origin digest, Development Workspace and its configuration snapshot, separate Execution Node, references, notes, runs and a previous-revision journal digest. Each write preserves prior raw bytes, then atomically replaces the head. Read/write limits are 4,000,000 UTF-8 bytes. History snapshots are content-addressed and immutable; revision and local locks are mandatory. Corrupt records are not reconstructed automatically. Resume neither writes nor submits.

Imports are raw content-addressed blobs under coordination/imports/snapshots, retaining original path/type. Changed sources create new snapshots; conflicts stop. Tasks bind study, code and compute; a run ID cannot change task. Registered run snapshots bind task/raw digest and node, but require actual-node inspection. Historical expired approvals may be archived without extension. Study state is outside Git and requires whole-state backup. Code, data, models, dependencies, credentials and runtime records do not synchronize automatically.

Supporting and historical records

Simulation Lab

Purpose and contract

The pure-Python Sum Calculation (sum-v1) and Quadratic Calculation (quadratic-v1) adapters exercise one lifecycle without networking, licenses or professional tools. They validate software interfaces and durable records, not scientific conclusions or production approval.

Preflight verifies registration, API version and implementation/engine hashes; prepare bounds finite parameters and freezes a request; submit records a queued state and immediately returns a simulation ID; query/cancel reload state and cancel queued work; collect checks raw artifact digests; validate independently recomputes the example result. Real tools still need installation/license/resources, locked data/environment, actual scheduler submission/query/cancellation, bulk collection and scientific units/convergence/sensitivity acceptance.

State is stored under simulation-runs/<ID> in the selected store. Identical ID/request retries return the original state; conflicting reuse fails. A restarted process queries the same directory without resubmission. Advance explicitly progresses queued → running → finished. There is no daemon: queued work does not execute after the terminal closes. Interrupted running state is not automatically rerun or declared cancelled; reconcile the original ID. Preserve incomplete disk-failure directories instead of deleting them to reuse an ID.

python -B scripts/simulation.py --store ../simulation-store collect --id SIM-001
python -B scripts/simulation.py --store ../simulation-store validate --id SIM-001

Updating OpenSci

Upgrade with your data and settings intact

Before every upgrade, back up all your data and verify that backup. Read the complete backup checklist. Include research folders, Zotero and external credentials as applicable; the updater cannot discover every file you use. Keep a second copy on a separate, protected device or encrypted backup service. Another folder on the same disk protects against an update mistake, not disk loss.

OpenSci 1.1.0 adds Update-OpenSci.cmd on Windows and scripts/update_runtime.py for command-line use. The updater changes only files in the reviewed software manifest. It preserves .local.* configuration, Study records, extra user files and the encrypted connection store. It neither removes retired files nor migrates Study formats, rewrites settings, starts experiments, or enables connections. It stops on edited/missing managed files, new-path conflicts, invalid packages, or detected concurrent changes. No software can guarantee safety against an actively writing external application; stopping writers is still required.

Windows: ordinary updates from 1.1.0 onward

  1. In File Explorer open the existing installation folder (for example C:\OpenSci) and double-click Update-OpenSci.cmd. Your configured Python must still exist. Use 1 to check the newest stable version, 2 to download and prepare it, or 3 to use a previously downloaded full runtime ZIP. Version checking sends no local configuration or Study data.
  2. Choose an existing private folder outside the software and all data folders, for example create D:\OpenSci-Backups in File Explorer first. The tool creates a new dated, access-restricted subfolder. The automatic local backup is a ZIP, not encrypted; use an encrypted backup disk/storage for the independent copy.
  3. Check the displayed software and Study data paths. The Study path comes from config/studies.local.json; when absent, the installation is the legacy coordinator. Add any other research/data folders you want included, one full folder path at a time, then press Enter on a blank line. The current Windows user's existing OpenSci encrypted-connection directory is automatically included; it is copied as ciphertext, not decrypted.
  4. The tool verifies the archive checksum, exact file inventory and per-file hashes, then creates plan.json in the new update folder. Open it with Notepad. changes lists every software path that will change; before and after are file fingerprints. retained_retired_files lists old software kept on disk. Planning changes no installed files. A file-conflict diagnostic means your copy needs review; keep the custom file and do not delete it to force the upgrade.
  5. Complete and verify the independent backup checklist. Type BACKED UP only after doing so. The menu stops its managed background connection. Close other assistant/MCP connections, OpenSci sessions, observers, importers and editors; finish or reconcile pending save receipts. Type STOPPED to attest that all other writers are stopped, then UPDATE to approve the displayed plan. These words are operator assertions, not automatic detection of every program.
  6. Before replacing any software, the updater makes and verifies a full-folder backup\backup.zip and backup\receipt.json. It rechecks file fingerprints before each replacement, preserves existing file permissions during replacement, and records progress in transaction.json. A tiny .opensci-update.lock remains in the installation as an inert concurrency lock; it contains no user data.
  7. When the result says updated: true, verify the new version and your saved Study Overview. Open Start-Study-Chat.cmd if you want to resume a stored-key connection. Its encrypted key and sign-in preference are retained. No data migration or new Study selection is performed. Keep backups until you have checked your actual research work.

First upgrade from 1.0.1

Version 1.0.1 does not have the new updater. Download OpenSci-1.1.0.zip and SHA256SUMS.txt from the official release. Match the ZIP's SHA-256 against that file before running code. In Windows, search Start for PowerShell, open it and paste the following command, replacing the ZIP path with the downloaded file's actual location:

Get-FileHash -LiteralPath 'C:\Users\YOURNAME\Downloads\OpenSci-1.1.0.zip' -Algorithm SHA256

If it matches, right-click the ZIP in File Explorer and Extract All into a new folder. Find the inner folder containing Update-OpenSci.ps1. Run this in PowerShell, replacing the first path with that extracted script's location and C:\OpenSci with the existing installation:

powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\Downloads\OpenSci-1.1.0\Update-OpenSci.ps1' -RuntimeRoot 'C:\OpenSci'

This execution policy applies only to this process. Choose 3, provide the downloaded runtime ZIP and its trusted checksum, and follow the normal backup/plan/apply steps above. Keep the extracted updater until the upgrade is complete. Do not extract a release directly over an existing installation. A Git clone's customized source needs review; the updater does not commit, stash or merge Git work.

Interrupted update

Keep all writers stopped. Do not simply rerun Apply or delete transaction.json. Open the updater from the intact extracted package if the installed copy cannot start, choose 5, and supply the full path to the failed update's transaction.json. A transaction in applying or recovery_required state can restore the earlier software bytes from its verified backup. Recovery refuses files edited since the interruption. It removes only unchanged new software files introduced by that transaction; it never restores older Study/configuration data over newer records. It does not provide a one-click downgrade of a completed update.

After recovery says recovered: true, inspect the original failure, verify the old installation and prepare a new plan in a new folder. If recovery reports a conflict, preserve both copies and seek maintenance help. Full data restoration is a separate operation into a new empty destination, described in the backup guide.

Command-line entry (Windows or Linux)

In a terminal opened in the extracted verified release, use your configured Python (python3 on many Linux systems). Replace every path and TRUSTED_ZIP_SHA256 with your real values. --extra may be repeated for additional explicitly selected folders. The pure-Python maintenance tool does not install a Linux credential service.

python -B scripts/update_runtime.py check
python -B scripts/update_runtime.py download --output /private/new-download
python -B scripts/update_runtime.py plan --package /private/OpenSci-1.1.0.zip --sha256 TRUSTED_ZIP_SHA256 --runtime /opt/OpenSci --coordinator /srv/OpenSci-Data --work /private/new-update
python -B scripts/update_runtime.py apply --plan /private/new-update/plan.json --quiesced --backup-confirmed
python -B scripts/update_runtime.py recover --transaction /private/new-update/transaction.json --quiesced

--quiesced asserts stopped writers; --backup-confirmed asserts your independent backup is ready. They do not perform those actions. Installers must have write permission to the selected installation; do not run a whole research assistant as administrator to bypass a file conflict. Checksums verify bytes; the official HTTPS release origin is the download trust source, not a cryptographic publisher signature.

Record maintenance and research source changes

Update source, study records and deployment settings as separate reviewed actions. An update never grants experiment approval or activates services automatically. History and Recovery explains record preservation; Maintenance Plans gives the operating procedure.

  1. Identify the Coordinator and all record writers. Stop writes, reconcile original run IDs and save a verified backup with its trusted digest stored separately.
  2. Verify the new package in an isolated directory. Preserve original source, Git history, local configuration, study records, evidence, literature operations and manuscripts.
  3. Review the source changes and shared rules. Maintain the same source identity and synchronize one reviewed commit to the intended workspaces.
  4. Run the affected checks on each target platform. Verify package hashes, both handbooks, launcher behavior and the actual integrations being used.
  5. If existing records require maintenance, prepare and review an explicit plan. Apply only against the unchanged record, configuration and source used for that plan.
  6. Hand over to one writer. Read the resulting study and history, verify receipts and inspect original run IDs before normal use.

Changed source or shared rules can change future review/task bindings even when the product version stays the same. Preserve frozen reviews and approval originals; never edit their digests to make them authorize changed work.

Planning recovery creates a new revision and preserves later evidence and runs. Restoring source does not undo external Zotero or Word effects.

Keep deployment reports, source snapshots, test output and configuration/cache ledgers in an archive outside the distribution. Current user documentation describes the current product; development chronology belongs in that archive.

Estimator Comparison Protocol

Synthetic experiment protocol

The Estimator Comparison protocol (record identifier synthetic-v1) applies to demo with public data; the task binds this file's SHA-256. Compare sample-mean and sample-median mean-squared error for the uncontaminated normal location 0. The contaminated mixture mean is 0.8, but the estimand remains 0; this cannot establish that the median better estimates the mixture mean. The proposed hypothesis is higher mean efficiency under clean normal data and higher median robustness under the specified contamination, not a verified real-world finding.

  • Clean observations are N(0,1).
  • Contaminated observations independently receive an added 8 with probability 0.1.
  • Within a trial, both estimators use the same sample; scenarios use distinct samples.
  • Defaults are seed=42, samples=100 and trials=100; approved parameters control the actual run.
  • Python random.Random generates clean then contaminated scenarios in fixed continuous order; exact Python version is fingerprinted.
  • The statistical unit is the trial, with trials rows per scenario. The dataset definition digest is a generator-definition hash, not a raw-data-file hash.

Each row records mean_error_sq and median_error_sq relative to 0. metrics.json stores average squared error for each estimator/scenario, four metrics total. Validation checks row counts, unique trial IDs, finite nonnegative metrics and CSV/JSON recomputation consistency. Software acceptance does not require either estimator to win.

Current code computes no confidence intervals, p-values or significance claims. A formal comparison should prespecify paired losses d_i = mean_error_sq_i - median_error_sq_i by scenario, report their mean and Monte Carlo standard error with a chosen interval method, and assess contamination/sample-size/offset sensitivity. Review, commit and approve the implementation, repetitions and stopping rule separately. Do not cherry-pick seeds, portray selected reruns as prespecified, or extrapolate to real medical/engineering/business data.

The adapter uses no GPU and declares one CPU thread; samples×trials is bounded by 10,000,000, with two actual scenarios. The executor enforces timeout; compute_budget is a human record, not a billing cap. Protocol/generator/parameter/dependency/node changes require a new run and approval; preserve old failures. Privacy and Data Handling

OpenSci is self-hosted software. The repository and release archives contain source, generic examples, documentation and plugin metadata. They contain no hosted account or connection. The publisher does not receive Study data merely because the software is installed.

Data stored by your installation

Your coordinator stores Study goals, progress, evidence references, operation receipts, immutable record history and permitted literature results. Research source, raw data, Zotero libraries and manuscripts may have separate locations. The local literature index is derived data. Connection policies contain scope and identity labels; logs and backups can also be sensitive. Choose access permissions, backup locations and retention appropriate to your research.

OpenSci does not include telemetry or a publisher-operated sync service. Explicit update checks/downloads contact the fixed public GitHub repository for release metadata and assets, without uploading local files or configuration. Full-folder backups remain local and contain sensitive configuration; their ZIP files are not encrypted. The tool creates private output folders, and users should put independent copies in encrypted, access-controlled storage. Optional operations can contact the services you configure: model providers receive the supplied review or analysis material; literature sources receive searches and permitted downloads; Zotero receives local API requests; SSH reaches the chosen node; MLflow and Prefect receive their configured records or work. A ChatGPT/assistant or tunnel connection also processes the tool inputs and outputs required for that interaction under the host provider's policies. No guarantee is made about an external provider's logging, retention or billing.

Credentials and access

Use local credential stores or environment references. Never put secret values in Study text, source, examples, issues, screenshots or committed configuration. The Windows tunnel launcher supports a one-time hidden prompt or optional Windows DPAPI CurrentUser encryption under the current user's LocalAppData OpenSci connection directory. The latter can run in the background and, by explicit selection, at Windows sign-in. Startup entries contain paths only. The key is decrypted for the tunnel process, not written as plaintext to source, configuration or logs. DPAPI does not isolate the key from other programs running as the same Windows user or from a compromised administrator account. Revoke or rotate it with its issuer when appropriate. A private connection policy limits selected Studies and tools, but same-account filesystem access is not an isolation boundary. Protect policies, source and coordinator records with operating-system permissions. Revoke grants and stop/restart the affected connection when access changes.

Zotero owns its database and attachment storage. OpenSci uses its local API, preserves instance identity and requires explicit grants for changes. Keep the local API on loopback. Search does not authorize collection, deletion, replacement or paid analysis.

Publishing your own copy

Keep .local.* files, credentials, connection profiles, personal research settings, raw data, Study records, manuscripts, result artifacts, logs, caches and backups outside Git. The release builder accepts only the explicit tools/release_files.json inventory and refuses unlisted working-tree files. Review that inventory and the staged content before publishing. Ignore rules do not remove already committed files or history.

The public package has no regression suite, test fixtures or test results. Development verification material is maintained outside this distribution. The runnable estimator example and calculation adapters are functional reference modules, with stated scientific limits; they contain no personal research data.

Reporting a problem

Use the repository's GitHub security reporting channel if enabled, or open an issue containing only a non-sensitive description and ask for a private reporting route. Do not post a key, private file, internal host name or real Study record. If a credential was exposed, revoke or rotate it with its issuer; removing a file or rewriting history cannot invalidate a credential or erase copies already downloaded.
